## Context

A team-built delivery platform for a MERN e-commerce application. The workflow connects Docker images, AWS provisioning, a self-managed Kubernetes cluster, Jenkins CI, and Argo CD deployment through Helm.

## Architecture

1. **Infrastructure:** Terraform provisions AWS resources; Ansible configures the self-managed Kubernetes cluster.
2. **Build and validation:** Jenkins builds the application image and integrates SonarQube quality gates and Trivy scans.
3. **Delivery:** Argo CD reconciles a Helm umbrella chart against the declared application configuration.
4. **Runtime:** Kubernetes namespaces organize workloads, and Horizontal Pod Autoscaling controls replica scaling.
5. **Operations:** Prometheus, Grafana, and Loki provide metrics, dashboards, and logs. Sealed Secrets stores encrypted secret manifests in the delivery workflow.

A post-sync hook initializes the MongoDB replica set after deployment. This step separates declarative workload creation from database-topology initialization.

## My contribution

I built and containerized the MERN application, provisioned AWS infrastructure, and automated cluster configuration. I also implemented Jenkins CI, the Argo CD and Helm delivery path, observability components, and Sealed Secrets integration within the team project.

## Design decisions

Terraform and Ansible divide resource provisioning from host and cluster configuration. Jenkins produces and validates artifacts; Argo CD handles deployment reconciliation. These responsibilities reduce ambiguity about which component changes infrastructure, publishes an image, or updates a running workload.

The self-managed cluster exposes Kubernetes networking and control-plane behavior, while adding maintenance work compared with a managed service. Database hooks need to tolerate repeated synchronization, and encrypted secret manifests still depend on the cluster's decryption-key lifecycle.

## Validation and scope

The project demonstrates an integrated delivery workflow, including quality checks, GitOps synchronization, and operational visibility. It does not report a measured availability target, deployment-frequency improvement, or recovery-time benchmark. The case study describes the implemented platform rather than an independently benchmarked production service.
